# CONTEXT

## Current implementation and bottlenecks

**The shipped bug, and why it is the right place to start.** Reproduced before
this plan was written. A binding of one function taking a `u21` and returning
`i8`, with no declared Zig errors, generates:

```rust
pub fn width(cp: u32) -> Result<i8, Error> {
    let (result, code) = raw::width(cp);
    if code != 0 {
        return Err(Error::from_code("width", code));
    }
    Ok(result)
}
```

and no `src/error.rs`, because `public.hasErrors` asks
`program.error_codes.len != 0` -- the *declared* errors. `rustc` reports
`error[E0425]: cannot find type 'Error' in this scope`.

The cause is worth stating precisely, because handles walk straight into it.
`lower.promoteCheckedFunctions` rewrites a function's return to
`error_union` **with an empty error set** whenever `reportsPanics` holds -- a
handle receiver, a handle parameter, or a narrow-integer parameter. That is the
rule the whole binding rests on: a native panic needs a channel to be reported
through, and without one Zig's fatal panic becomes a silent success. So:

- `origin.@"return" == .error_union` means *a status channel exists*.
- `function.errors.len == 0` alongside it means *no Zig error is declared*, so
  the only non-zero codes are `-4` (invalid handle) and `<= -256` (a caught
  native panic).

`Shape.fallible` currently conflates the two, which is why the crate references
an error type that was never emitted.

**Every handle method is promoted this way.** From `examples/03-opaque`'s
header, `fn add(self: *Context, value: i64) i64` -- infallible in Zig --
crosses as `int32_t zg_context_add(zg_context *self, int64_t value, int64_t
*out_result)`. Go therefore spells it `func (co *Context) Add(value int64)
(int64, error)`. Transplanting that into Rust would put a `?` on every method
call that Zig says cannot fail.

**The constructor-name rule is Go-shaped.** `Target.publicFunctionNameAlloc`
ends with `std.fmt.allocPrint(allocator, "New{s}", .{constructor.type})`. Plan
188 recorded this as creak 6 and left it, because the minimal backend had no
constructors. It has to move before handles land.

**What the C ABI offers**, read off the generated header rather than guessed:

| Zig | C |
|---|---|
| `Context.create() CreateError!*Context` | `int32_t zg_context_create(zg_context **out_result)` |
| `Context.add(self: *Context, v: i64) i64` | `int32_t zg_context_add(zg_context *self, int64_t v, int64_t *out_result)` |
| `Context.addCopy(self: Context, v: i64) i64` | `int32_t zg_context_add_copy(const zg_context *self, ...)` |
| `Context.deinit(self: *Context) void` | `int32_t zg_context_deinit(zg_context *self)` |
| `Context.borrowView(self: *Context) *ContextView` | `int32_t zg_context_borrow_view(zg_context *self, zg_context_view **out_result)` |
| `sumCopies(bias, left: Context, right: Context)` | `int32_t zg_sum_copies(int64_t, const zg_context *, const zg_context *, int64_t *)` |
| a caller-owned buffer | `int32_t zg_take_owned(const uint8_t **out_ptr, size_t *out_len)` plus `void zg_free_owned(const uint8_t *, size_t)` |

The opaque type is `typedef struct zg_context zg_context;` -- incomplete, so
Rust names it with an `extern type`-shaped placeholder rather than pretending
to know its layout.

## Target structure and invariants

Invariants that hold at every commit:

- **Go's generated bytes never change.** 77 generator cases and thirteen
  examples check it every phase.
- **The C ABI shim, the panic source and the C header stay shared and
  unedited.** A handle concept appearing in `emit/shim.zig` or
  `emit/header.zig` means the design is wrong.
- **`src/gen/emit/**` gains no Rust knowledge and `src/gen/emit_rust/**` gains
  no Go knowledge.** They meet at `neutral_emitters`, `Emitter`, `Options` and
  `abi.Program`.
- **A shape this plan refuses is refused with `ZIGO060` naming the declaration
  and the feature**, before the output tree is touched. Never skipped silently.
- **No `ir_version` change and no IR field added.** Everything this plan needs
  is already lowered: `program.handles`, `AbiOpaque.lifecycle`,
  `Ownership.Handle`, `Ownership.BorrowedView`, `Ownership.Buffer`.

**The status-channel decision, stated once.** A call whose C return is a status
code but whose Zig signature declares no error set can only report a bug: `-4`
is an invalid handle, which a Rust wrapper makes unreachable by owning a
non-null pointer for its whole life, and `<= -256` is a caught Zig panic, which
is a defect in the bound library. Rust's vehicle for a defect in the callee is
a panic, so such a call returns `T` and panics with the native message. A call
whose Zig signature *does* declare errors keeps `Result<T, Error>`, and
`ErrorKind::NativePanic` stays a variant there.

This is a better mapping than Go's and it costs nothing that works today: a
declared-error function is unchanged, a channel-free function is unchanged, and
the only functions affected are the ones that currently fail to compile.

The destructor is the exception and needs its own sentence: `Drop` cannot
return and must not panic (a panic while unwinding aborts), so the destructor's
status is deliberately discarded. The generated `Drop` says so.

**The handle shape:**

```rust
/// A handle to the native `Context`.
///
/// The native object is released when this value is dropped. Not `Send` or
/// `Sync`: whether the bound library's object may cross threads is a fact
/// about that library which zigo does not record.
pub struct Context {
    handle: *mut raw::zg_context,
}

impl Context {
    pub fn create() -> Result<Self, Error> { ... }        // declares an error set
    pub fn add(&mut self, value: i64) -> i64 { ... }      // `*Context`
    pub fn add_copy(&self, value: i64) -> i64 { ... }     // `*const Context`
    pub fn borrow_view(&self) -> ContextView<'_> { ... }  // borrowed view
}

impl Drop for Context {
    fn drop(&mut self) { ... }
}
```

**The borrowed view** is a separate type with a lifetime and no `Drop`:

```rust
pub struct ContextView<'owner> {
    handle: *mut raw::zg_context_view,
    owner: core::marker::PhantomData<&'owner ()>,
}
```

`PhantomData<&'owner ()>` rather than `&'owner Context`, so the view does not
also claim to borrow the owner's *type* -- only its lifetime.

**The owning buffer** is one generic type, not one per release function:

```rust
pub struct OwnedSlice<T: 'static> {
    ptr: *const T,
    len: usize,
    release: unsafe extern "C" fn(*const T, usize),
}
```

with `Deref<Target = [T]>` and a `Drop` that calls `release`. One type keeps
the naming question from arising at all: a release function shared by three
returns would otherwise need a name none of the three own. A UTF-8 buffer
derefs to `[u8]` like any other and the caller converts; the generated doc says
so. Special-casing text into `String` would put the copy back.
